# Изменения API для мобильного разработчика

## 4. 🆕 Блокировка пользователей и коды причин жалоб (Apple Guideline 1.2)

**Период:** 19–20 августа 2026 · **База:** `/api/v1`

**Главное — локальное хранилище блокировок в приложении НЕ нужно.** Блокировки
теперь серверные: после `POST /blocks` сервер сам исключает объявления
заблокированных авторов из `/search*` (выдача и карта), скрывает тред из
`GET /chat/threads` и отвечает `403` на отправку сообщений в обе стороны.
Приложение только дергает ручки ниже и рисует экран «Заблокированные» из
`GET /blocks`. Детальная страница объявления по прямой ссылке остаётся
доступной (блок скрывает из discovery, не из прямого доступа).

### 4.1. Заблокировать — `POST /api/v1/blocks`

- **Auth:** обязательная (Bearer).
- **Body:** `{ "user_id": "<uuid>" }` — кого блокируем (id продавца =
  `owner_id` объявления или `counterparty.id` треда).
- **Ответы:** `201 { id, user_id, created_at }`; повторный блок — идемпотентно
  `201` с той же строкой; `400` self-block; `404` нет такого пользователя;
  `401` без токена.

### 4.2. Разблокировать — `DELETE /api/v1/blocks/:userId`

- `204` всегда (идемпотентно, даже если блока не было).

### 4.3. Список — `GET /api/v1/blocks`

- `200 { "data": [{ "user_id", "name", "avatar_url", "blocked_at" }] }`,
  свежие сверху, без пагинации.

### 4.4. Жалобы: словарь причин `POST /api/v1/complaints`

`reason` теперь передаём одним из кодов (контракт, сервер строку не валидирует
по enum): `SPAM | FRAUD | WRONG_INFO | OFFENSIVE | ALREADY_SOLD | OTHER`.
`details` — свободный текст, для `OTHER` просим комментарий на клиенте.
Жалоба из чата — тот же эндпоинт с `listing_id` треда. Рекомендованный флоу
блокировки из чата: `POST /complaints` (уведомление модерации) +
`POST /blocks`.

## 1. 🆕 Обращения в поддержку (форма /help)

Новый модуль. Три ручки.

### 1.1. Создать обращение — публичная

```
POST /api/v1/support/requests
```

- **Auth:** опциональная (см. раздел «Авторизация» ниже).
- **Rate-limit:** 5 запросов / 60 сек с одного IP (антиспам).

**Body:**

| Поле      | Тип    | Обяз. | Ограничения       |
|-----------|--------|-------|-------------------|
| `name`    | string | нет   | ≤ 120 символов    |
| `contact` | string | **да**| 3..160 символов   |
| `message` | string | **да**| 3..5000 символов  |

**Ответ `201`:**

```json
{ "id": "uuid", "status": "NEW" }
```

> `contact` — как связаться (телефон/email). Обязателен, т.к. отправлять может гость
> без аккаунта.

### 1.2. Авторизация — гость может отправить

Ручка под «мягким» гардом:

| Ситуация                          | Результат                                          |
|-----------------------------------|----------------------------------------------------|
| Без заголовка `Authorization`     | ✅ Проходит как гость → `user_id = null`            |
| С валидным Bearer                 | ✅ Проходит → обращение привязано к `user_id`       |
| С битым / просроченным токеном    | ❌ `401`                                            |

**Правило для клиента:** либо не слать заголовок `Authorization` вообще, либо слать
только валидный токен. Пустой/протухший токен «на всякий случай» даёт `401`.

### 1.3. Админские ручки (роль MODERATOR / ADMIN)

К обычному мобильному клиенту не относятся — только если приложение админское.

```
GET /api/v1/admin/support/requests?status=&page=&limit=
```
Ответ:
```json
{
  "data": [ /* SupportRequest[] */ ],
  "meta": { "page": 1, "limit": 20, "total": 0 }
}
```
`limit` по умолчанию `20`, максимум `100`. `status` — необязательный фильтр.

```
PATCH /api/v1/admin/support/requests/:id
Body: { "status": "NEW" | "IN_REVIEW" | "RESOLVED" }
```
Проставляет `handled_by` (модератор из токена) и `handled_at` (текущее время).
`404`, если обращения нет.

### 1.4. Объект `SupportRequest` (админ-контракт, snake_case, даты ISO)

```json
{
  "id": "uuid",
  "user_id": "uuid | null",
  "name": "string | null",
  "contact": "string",
  "message": "string",
  "status": "NEW | IN_REVIEW | RESOLVED",
  "handled_by": "uuid | null",
  "handled_at": "ISO string | null",
  "created_at": "ISO string"
}
```

**Статус** — только 3 значения: `NEW`, `IN_REVIEW`, `RESOLVED`. «Отклонить»
обращение нельзя — только решить.

## 3. 📞 Формат телефона — E.164

Контракт: телефон отправляется в формате **E.164** — `+998XXXXXXXXX`
(ровно 9 цифр абонента после кода страны).

Касается полей:

| Поле              | Где                          |
|-------------------|------------------------------|
| `contact_phone`   | профиль / `me`               |
| `requester_phone` | запрос на тур (Tour Request) |
| телефон при логине| Login                        |

**Для мобилки:** нормализуй ввод пользователя в `+998...` перед отправкой.
Изменения пока сделаны в web-клиенте, но серверный контракт ожидает E.164.

## Итог (что делать на мобилке)

1. Добавить экран «Поддержка» → `POST /support/requests` (можно от гостя, `contact`
   обязателен, помнить про rate-limit 5/60с).
2. Показывать поле `address` в «Мои объявления».
3. Слать телефон везде в формате `+998XXXXXXXXX`.
