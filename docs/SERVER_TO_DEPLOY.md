# Avino — выбор сервера для деплоя и план масштабирования

> Анализ под текущую архитектуру (single-host Docker Compose за Caddy).
> Цифры стоимости — ориентировочные, начало 2026; ёмкость по нагрузке — оценки,
> уточняются по факту через мониторинг. Аудитория: Узбекистан / СНГ (`avino.uz`).

---

## TL;DR

| Вопрос | Ответ |
|--------|-------|
| **С чего начинать (medium)** | **1 VPS: 4 vCPU / 8 GB RAM / 160 GB NVMe** — весь стек на одном боксе. Hetzner CPX31 (~€16/мес) или DigitalOcean 4 vCPU/8 GB (~$48/мес). |
| **Можно ли дешевле на старте** | Да: 2 vCPU / 4 GB для closed-beta, но сборку Next.js выносить в CI (иначе OOM при `next build`). |
| **Когда расширять** | По метрикам: CPU > 70% устойчиво, RAM (без кеша) > 80%, p95 API > 300–500 мс на тёплом кеше, диск > 75%, рост очередей BullMQ. |
| **Как расширять** | Вертикально (8 vCPU/16 GB) → затем вынести Postgres на отдельный/managed узел + PgBouncer → затем горизонтально (2+ stateless узла client/web/api за балансировщиком, отдельный Redis, CDN перед порталом). |
| **Главный сюрприз** | `next build` двух Next-приложений съедает 2–4 GB RAM. На маленьком боксе нужен swap **или** сборка образов в GitHub Actions с последующим `pull`. |

## 1. Что реально крутится

Деплой — **монолит на одном VPS**: 6 контейнеров Docker Compose за Caddy
(`docker-compose.yml` + `docker-compose.prod.yml`, разворот `deploy/deploy.sh`).

| Контейнер | Технология | Порт | Роль |
|-----------|-----------|------|------|
| `postgres` | PostgreSQL 16 + **PostGIS 3.4** | 5432 (внутр.) | Основная БД + гео-запросы (районы, polygon-поиск, trigram) |
| `redis` | Redis 7 | 6379 (внутр.) | Кеш + очереди **BullMQ** (promotions, translations, email, saved-search) |
| `api` | **NestJS 10** (Node 20) | 4000 (внутр.) | REST API + BullMQ-воркеры в том же процессе |
| `web` | **Next.js** (SSR) | 3000 (внутр.) | Админка |
| `client` | **Next.js** (SSR) | 3001 (внутр.) | Публичный портал (основной пользовательский трафик) |
| `caddy` | Caddy 2 | **80/443 (+443/udp HTTP/3)** | Reverse-proxy, авто-TLS (Let's Encrypt), gzip/zstd |

**Внешние зависимости (не на боксе — важно для сайзинга):**

- **Cloudflare R2** — всё медиа (фото объявлений). Диск и egress сервера этим **не нагружаются** — большая экономия. См. `docs/GUIDE_S3.md`.
- **SMTP (транзакционный)** — вход завязан на EMAIL-OTP. Нужен внешний провайдер
  (Amazon SES / Resend / Postmark): Hetzner и многие VPS блокируют исходящий порт 25.
- **Yandex Maps JS API** — карта и гео-подсказки исполняются в браузере клиента.
- **Google OAuth**, **Telegram** алерты — внешние API, нагрузки на сервер не дают.

**Вывод по профилю:** stateless фронт (две Next-витрины + API) + stateful ядро
(Postgres + Redis) на одной машине. Медиа вынесено. Это классический кандидат на
«начать с одного VPS → растащить по узлам по мере роста».

## 2. Допущения по нагрузке

- Аудитория CIS, основной трафик — публичный портал `client` (SSR, чтение-тяжёлый:
  поиск, карта, карточки). Админка `web` — низкий трафик (модераторы).
- Запись (создание/редактирование объявлений, модерация, чат) — заметно меньше чтения.
- Медиа отдаётся напрямую из R2 (presigned/CDN), не через сервер.
- Тяжёлые фоновые задачи (переводы, email, промо, saved-search) — асинхронно через
  BullMQ, не блокируют HTTP-путь.

## 3. Бюджет ресурсов на одном боксе

| Сервис | RAM (покой) | RAM (под нагрузкой) | CPU |
|--------|------------:|--------------------:|-----|
| postgres + postgis | 256–512 MB | 1–2 GB (shared_buffers + work_mem) | пики на гео/сортировке |
| redis | 30–80 MB | 100–300 MB | низкий |
| api (NestJS + воркеры) | 150–250 MB | 300–600 MB | средний-высокий |
| client (Next SSR, портал) | 150–250 MB | 300–600 MB | **высокий** (публичный трафик) |
| web (Next SSR, админка) | 120–200 MB | 200–400 MB | средний |
| caddy | 20–40 MB | 50–100 MB | низкий |
| ОС + Docker | 300–500 MB | ~500 MB | — |
| **Итого рантайм** | **~1.2–1.8 GB** | **~3–4.5 GB** | — |

⚠️ **Пик сборки.** `next build` каждого Next-приложения отъедает ~1.5–2 GB.
Сборка обоих + NestJS на боксе кратковременно требует **+2–4 GB** сверх рантайма.
Поэтому 8 GB собирает спокойно; 4 GB — впритык (нужен swap); 2 GB — OOM без
готовых образов из CI. (В памяти проекта уже зафиксированы случаи порчи `.next`.)

## 4. Тиры серверов

### T0 — Минимальный старт (бюджет / closed-beta)
**2 vCPU / 4 GB RAM / 80 GB NVMe**
- Hetzner **CPX21** (3 vCPU / 4 GB / 80 GB, ~€8/мес) или **CX32** (4 vCPU / 8 GB).
- DigitalOcean 2 vCPU / 4 GB Premium (~$24/мес).
- Условие: **swap 4 GB** или (лучше) сборка образов в GitHub Actions + `pull` на прод.
- Ёмкость (оценка): первые сотни пользователей, ~10–20k запросов/день.

### T1 — Рекомендуемый старт (medium) ⭐
**4 vCPU / 8 GB RAM / 160 GB NVMe**
- Hetzner **CPX31** (4 vCPU / 8 GB / 160 GB, ~€16/мес) — лучший value.
- Hetzner **CCX13** (2 dedicated vCPU / 8 GB) — если нужен стабильный CPU без «соседей».
- DigitalOcean 4 vCPU / 8 GB (~$48/мес).
- Сборка на боксе комфортна, рантайм с запасом на пики и BullMQ.
- Ёмкость (оценка): ~3–10k уникальных/день, сотни одновременных сессий,
  p95 API < 200 мс на тёплом кеше.

### T2 — Рост (больше пользователей)
**8 vCPU / 16 GB RAM / 240+ GB**, либо начать раздвигать ядро:
- Hetzner **CCX23/CCX33** (dedicated CPU), DO 8 vCPU / 16 GB.
- Первый шаг декомпозиции: **вынести Postgres** на отдельный узел (или managed:
  DO Managed Postgres с PostGIS), добавить **PgBouncer** (пул соединений).
- Ёмкость (оценка): десятки тысяч/день.

### T3 — Масштаб (scale-out, HA)
Разнести по узлам:
- **Managed Postgres (PostGIS)** + read-replica для тяжёлого чтения/поиска.
- **Отдельный Redis** (managed или свой узел).
- **2+ stateless узла** `client`/`web`/`api` за балансировщиком (они без состояния —
  масштабируются горизонтально).
- **Вынести BullMQ-воркеры** в отдельный процесс/узел (отделить фон от HTTP).
- **CDN перед порталом** (Cloudflare — уже используется R2): кеш статики и edge-TLS
  ближе к пользователю в UZ.

## 5. Триггеры апгрейда (по чему понимать, что пора расширять)

| Метрика | Порог | Действие |
|---------|-------|----------|
| CPU (5-мин avg) | > 70% устойчиво | +ядра (вертикально), затем горизонталь client/api |
| RAM без кеша / OOM-kills / своп-трешинг | > 80% | +RAM или вынести Postgres |
| p95 latency API на тёплом кеше | > 300–500 мс | профилировать запросы → PgBouncer → scale |
| Соединения Postgres | близко к `max_connections` | **PgBouncer**, затем managed PG |
| Redis memory | > 70% `maxmemory` | bump / отдельный Redis |
| Диск | > 75% | расширить том; чистить docker build cache + логи |
| Backlog очередей BullMQ растёт | задержка обработки | отдельный worker-узел / больше concurrency |

## 6. Узкие места и как их снимать

1. **Next.js build OOM** — самый частый сюрприз на малом VPS.
   → 8 GB бокс, **или** swap, **или** (рекомендуется на проде) собирать образы в
   GitHub Actions и `docker pull` — быстрее деплой и не грузит прод. При нужде —
   `NODE_OPTIONS=--max-old-space-size=…`.
2. **Postgres делит RAM/IO с приложением** — на росте конкурируют. Первый кандидат
   на вынос в T2.
3. **SSR публичного портала (`client`)** — CPU-bound под трафиком. Первый кандидат на
   горизонтальное масштабирование + CDN/edge-кеш.
4. **Single point of failure** — один бокс = нет HA. Для medium приемлемо при
   надёжных бэкапах и быстром rebuild; для scale (T3) → multi-node.
5. **SMTP** — исходящий 25 заблокирован у многих VPS, а OTP-логин завязан на email.
   → обязательно внешний транзакционный провайдер (SES/Resend/Postmark). Уже в дизайне.

## 7. Регион и латентность (UZ / CIS)

- **Hetzner** (Falkenstein/Helsinki) → Ташкент ~80–120 мс. Дёшево и стабильно —
  оптимально по цене/качеству для старта.
- **DigitalOcean** (Frankfurt/Amsterdam) — сопоставимо; плюс — знаком по taplinks.
- Локальные/ближние DC (UZ-хостинги, Казахстан) дают меньшую латентность, но хуже по
  цене/инструментам и платёжным нюансам — рассматривать на T2–T3, если латентность
  станет проблемой.
- **CDN Cloudflare перед `client`/`web`** рекомендуется в любом тире: edge-TLS и кеш
  статики приближают отдачу к пользователю и сглаживают латентность до origin.
  R2 уже на Cloudflare — экосистема одна.

## 8. Эксплуатация (что не забыть на любом тире)

- **Бэкапы:** ночной `pg_dump` (cron) в офсайт (можно в отдельный R2-бакет) +
  снапшоты тома провайдером. Тома `avino-postgres-data` и `caddy-data`
  (сертификаты LE) — критичные. Рецепт дампа — в `deploy/README.md`.
- **Мониторинг:** минимум — алерты на диск/RAM/CPU провайдера + `docker stats`.
  Лучше — node_exporter + cAdvisor + Grafana (стек уже знаком по другим проектам)
  или Netdata одной командой.
- **`trust proxy`:** за Caddy для корректного rate-limit по IP добавить
  `app.set('trust proxy', 1)` в `apps/api/src/main.ts` (отмечено в `deploy/README.md`).
- **Диск:** медиа в R2 (диск не растёт от загрузок), но `docker` build-cache, образы и
  логи копятся → периодический `docker system prune` и ротация логов.
- **Файрвол:** наружу только 22 / 80 / 443; Postgres и Redis на хост не публикуются
  (prod-overlay уже снимает публикацию портов).

## 9. Чеклист быстрого старта (T1, medium)

1. Взять VPS **4 vCPU / 8 GB / 160 GB NVMe** (Hetzner CPX31 или DO-эквивалент),
   регион EU (или ближе к UZ).
2. Поставить Docker + Compose **v2.24+**, открыть 22/80/443.
3. Три DNS A-записи → IP: `avino.uz` (client), `admin.avino.uz` (web),
   `api.avino.uz` (api) — **до** первого запуска (Caddy выпускает TLS по HTTP-01).
4. `.env`: домены, `ACME_EMAIL`, сильные `POSTGRES_PASSWORD` и `JWT_*`, SMTP-провайдер,
   `S3_*` (R2). Шаблон — `deploy/prod.env.example`.
5. `./deploy/deploy.sh` (валидация → сборка → up → health-check).
6. Настроить ночной `pg_dump` в офсайт и алерты на ресурсы.
7. Опционально сразу: Cloudflare перед доменами (CDN + edge-TLS).
