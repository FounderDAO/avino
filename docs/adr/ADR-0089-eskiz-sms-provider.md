# ADR-0089 — Eskiz SMS provider: hardening, moderation and runbook

## Status

Accepted

## Date

2026-06-18

## Context

ADR-0012 зафиксировал Eskiz.uz провайдером SMS и поставил happy-path
`SmsService` (login → кэш токена → send → релогин при 401 → dev-fallback). Этого
достаточно для прохождения OTP-flow локально, но для production не хватало
операционной зрелости:

1. **Непрозрачные сбои.** При отказе отправки логировался только HTTP-статус
   (`Eskiz send failed: 400`), без причины от Eskiz. А самая частая причина в
   проде — **текст не прошёл модерацию шаблона** — оставалась невидимой.
2. **Нет тестов.** У всех auth-модулей есть `*.spec.ts`, у `SmsService` — нет.
3. **Нет runbook.** Для S3 есть `GUIDE_S3.md`; для SMS — ничего: что завести в
   кабинете Eskiz, какой текст подать на модерацию, какой sender, как принять.
4. **Модерация не задокументирована.** Реальность Eskiz: произвольный текст с
   боевого sender'а не уходит — и текст, и sender проходят модерацию.

Team Lead подтвердил: аккаунт Eskiz + одобренный шаблон есть → живая end-to-end
проверка отправки OTP входит в scope.

## Decision

- **Подтвердить Eskiz.uz** провайдером SMS (CLAUDE.md §13 — смена требует
  подтверждения; данным ADR решение переподтверждено).
- **Разбор ответа Eskiz** в `sendViaEskiz`:
  - успех → `LOG` с `id`/`status` и **маскированным** номером (`998****4567`);
    текст сообщения и полный номер в лог не пишем (приватность);
  - не-`401` ошибка → причина из поля `message` ответа Eskiz прокидывается и в
    лог (`ERROR`), и в текст исключения. Это делает отказ модерации диагностируемым;
  - `401` → как и раньше: сброс токена, релогин, один ретрай отправки.
- **Контракт не меняется.** `sendOtp(phone, code)` и dev-fallback (код в лог вне
  production) остаются прежними — `OtpService`/`AuthModule` не затронуты.
- **Юнит-тесты** `sms.service.spec.ts` (10 кейсов): dev-fallback, prod-без-кредов,
  happy-path (нормализация номера, `from`, Bearer), кэш токена, 401-ретрай
  (успех/провал), сбой логина, отсутствие токена, surfacing причины модерации,
  текст OTP.
- **Документация:** `docs/GUIDE_SMS.md` (runbook: аккаунт → модерация шаблона и
  sender → env → приёмка → troubleshooting); строка `ESKIZ_FROM` в `ENV.md` §11.
- **Намеренно НЕ реализовано (follow-ups):** программная проверка баланса
  (`/user/get-limit`), `callback_url` (статус доставки), batch-send, хранение
  токена в Redis. Для MVP не нужны; задокументированы в GUIDE_SMS §6.

## Consequences

Positive:
- Сбои отправки диагностируемы из логов — причина Eskiz (в т.ч. модерация) видна
  сразу, без воспроизведения.
- `SmsService` покрыт тестами наравне с остальным auth-слоем.
- Перевод в production — по чек-листу `GUIDE_SMS.md`, без поиска знаний заново.
- Логи доставки безопасны: без текста и без полного номера.

Negative / trade-offs:
- Модерация шаблона/sender — внешний ручной гейт Eskiz; любое изменение текста
  OTP в коде требует повторной модерации, иначе боевая отправка падает.
- Баланс и статус доставки не автоматизированы (баланс — ручной `curl` из
  runbook); при исчерпании баланса отправка падает без проактивного алерта.
- Токен Eskiz по-прежнему в памяти процесса (как в ADR-0012): несколько инстансов
  логинятся независимо — для MVP приемлемо.
