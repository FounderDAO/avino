# ADR-0099 — Фоновая чистка осиротевших фото в R2 (media-cleanup worker)

## Status
Accepted

## Date
2026-06-21

## Context
Фото объявлений хранятся в S3-совместимом R2 (ADR-0008/0086): в `listing_media`
лежит `storage_key` (source of truth), сам файл — в бакете. При удалении медиа
(`DELETE /listings/:id/media/:mediaId`, `ListingMediaService.remove`) сначала
удаляется строка БД, затем **best-effort** удаляется R2-объект. Если
`DeleteObjectCommand` падает, ошибка проглатывается (`logger.warn`) — комментарий
обещал «cleanup-джобу (API.md §8)», но её **не существовало**. Второй источник
сирот: в `uploadFile` объект сначала льётся в R2 (`uploads.upload`), затем
создаётся строка (`listingMedia.create`) — если create упадёт, объект осиротеет
сразу.

В результате осиротевшие объекты копились в бакете без какой-либо уборки. На
объёмах MVP это не критично, но это незакрытый технический долг и рост расходов
на хранение.

Удаление объектов — операция деструктивная, поэтому к ней предъявлены повышенные
требования безопасности: ошибочно удалённое живое фото исчезнет с карточки
объявления.

## Decision
1. **Бакет-свип без новой таблицы/миграции.** Новый
   `MediaCleanupService.run()` (по образцу `PromotionExpiryService`/
   `SavedSearchAlertService`) перечисляет объекты под префиксом `listings/`
   (`UploadsService.listKeys` — пагинированный `ListObjectsV2`), берёт только
   ключи медиа (фильтр по подстроке `/media/`), удаляет осиротевшие.
2. **Grace-окно.** Кандидатами становятся только объекты **старше**
   `MEDIA_CLEANUP_GRACE_HOURS` (по умолчанию 24ч): свежезагруженный файл, чья
   строка `listing_media` могла ещё коммититься в момент скана, не трогается.
3. **«Живой ключ» = `storage_key ?? extractKey(url)`** — ровно как в delete-пути
   (`ListingMediaService.remove`). Это гарантирует, что legacy-строки
   (`storage_key = NULL`, ключ восстанавливается из сохранённого `url`) не
   удаляются по ошибке. DB-запрос ограничен: `WHERE storage_key IN (<кандидаты>)
   OR storage_key IS NULL` (модерн-строки бьются по кандидатам, legacy — все,
   множество конечное и убывающее после ADR-0086).
4. **Батч.** `MEDIA_CLEANUP_BATCH_SIZE` (по умолчанию 500) ограничивает число
   удалений за прогон; большой бэклог сирот вычерпывается за несколько прогонов.
   Ошибка удаления одного объекта логируется и не валит прогон.
5. **Config-gated, по умолчанию ВЫКЛЮЧЕНО.** `MEDIA_CLEANUP_ENABLED` (default
   `false`). И продюсер (`MediaCleanupQueue`), и воркер (`MediaCleanupWorker`)
   при выключенном флаге — полный NO-OP: продюсер не создаёт BullMQ `Queue`
   (не открывает Redis-соединение) и не ставит repeatable-джобу; воркер не
   стартует. Расписание — `MEDIA_CLEANUP_CRON` (default `0 4 * * *`, раз в сутки):
   уборка не требует срочности.

## Consequences
- **Плюсы.** Нет миграции схемы; самовосстановление обоих источников сирот;
  безопасный выкат (флаг по умолчанию выключен — на staging/prod включается
  явно через `MEDIA_CLEANUP_ENABLED=true`); деструктивный код полностью
  изолирован от read/write-путей.
- **Trade-offs.** `listKeys` перечисляет ВСЕ объекты под `listings/` до применения
  батча — это неотъемлемо от orphan-детекции (нельзя узнать, что объект сирота,
  не сверив весь листинг с БД); батч ограничивает только удаления. На объёме
  миллионов объектов число round-trip'ов `ListObjectsV2` растёт — приемлемо для
  текущего масштаба, при росте → перейти на постраничную обработку или ledger.
- **Legacy-строки** (`storage_key = NULL`) грузятся из БД без key-фильтра
  (их ключ живёт только в `url`); множество конечное и убывает.

## Изоляция сред + предохранители (дополнение 2026-06-21)

**Проблема.** Свип удаляет объекты, у которых нет живой строки в `listing_media`
**своей** базы. Если несколько сред делят ОДИН бакет (у Avino локаль и staging
оба указывают на `avinodev` — staging-overlay не переопределяет `S3_*`, ключ был
плоский `listings/...`), то свип, запущенный в среде A, видит объекты среды B как
сирот (их строки в базе B) и **удалил бы живые фото B**. Grace-окно не спасает —
чужое фото давно вне 24ч.

**Решение — три слоя защиты:**
1. **`S3_KEY_PREFIX` (структурная гарантия).** Per-env неймспейс: новые фото
   пишутся в `{prefix}/listings/{id}/media/...`, а свип листит ТОЛЬКО
   `{prefix}/listings/`. Разные среды на общем бакете живут в непересекающихся
   поддеревьях → перекрёстное удаление **физически невозможно**. Дефолт пустой =
   плоский `listings/` (back-compat). Read-path не тронут (`storage_key` хранит
   полный ключ). Старые бес-префиксные объекты свип с заданным префиксом не
   трогает (безопасно — они просто не GC-ятся).
2. **`MEDIA_CLEANUP_DRY_RUN` (default `true`).** Наблюдательный режим: логирует
   `[DRY-RUN] would delete …`, удаляет НИЧЕГО. Первое включение всегда
   наблюдательное; в боевой режим — явным `false` после проверки лога.
3. **`MEDIA_CLEANUP_MAX_DELETE_RATIO` (default `0.5`) — circuit-breaker.** Если
   при выборке ≥20 объектов доля «сирот» выше порога — свип логирует `ABORT …` и
   прерывается, ничего не удаляя. Ловит «не та/пустая база» или забытый
   `S3_KEY_PREFIX` до катастрофы. `MIN_SAMPLE_FOR_RATIO=20` исключает ложные
   срабатывания на малых выборках.

**Принцип:** orphan-GC безопасен только когда одно поддерево ключей принадлежит
ровно одной базе. Префикс обеспечивает это структурно; dry-run и breaker —
операционные предохранители на случай ошибки конфигурации.

## Alternatives considered
- **Очередь отложенного удаления через новую таблицу** (записывать «удалить ключ K
  через N» при сбое best-effort delete). Отклонено: требует миграцию и не
  закрывает второй источник (upload без create); свип проще и самодостаточен.
- **Синхронный ретрай delete в `remove`.** Не закрывает сбой create и сбои,
  переживающие процесс; свип покрывает оба.

## Env
`MEDIA_CLEANUP_ENABLED` (default false), `MEDIA_CLEANUP_CRON` (`0 4 * * *`),
`MEDIA_CLEANUP_GRACE_HOURS` (24), `MEDIA_CLEANUP_BATCH_SIZE` (500),
`MEDIA_CLEANUP_DRY_RUN` (default true), `MEDIA_CLEANUP_MAX_DELETE_RATIO` (0.5) —
см. ENV.md §6.2. Изоляция сред — `S3_KEY_PREFIX` (ENV.md §9).
