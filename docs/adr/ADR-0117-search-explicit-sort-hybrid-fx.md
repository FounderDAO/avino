# ADR-0117 — Гибридная явная сортировка `/search` + FX-нормализация цены

## Status

Accepted

## Date

2026-06-30

## Context

QA публичного поиска выявил, что сортировка «Сначала дешёвые» (`sort=price_asc`)
визуально «не работает». Две независимые причины (обе подтверждены на живых
данных стенда, 64 объявления, смешанные валюты):

1. **Промо-тир доминирует над всей выдачей.** По ADR-0004 порядок —
   `effective_tier DESC, <secondary> <dir>, id DESC`, то есть promotion-тир ВСЕГДА
   первичный ключ. При «Сначала дешёвые» первыми идут все VIP/TOP (8+11 из 64), и
   реально самое дешёвое NORMAL-объявление (3 185 000 UZS ≈ $264) оказывается на
   ~19-й позиции, тогда как наверху — VIP за $64 300. Переключение сорта почти не
   меняет верх экрана → пользователь видит «ничего не произошло». У `price_desc`/
   `date_desc` тот же механизм незаметен (промо сверху смотрится естественно),
   поэтому жалоба именно на `price_asc`.

2. **Цена сортируется по сырому числу, без учёта валюты.** Вторичный ключ — голая
   колонка `price`. `64 300 USD` сортируется «дешевле», чем `7 035 000 UZS`
   (≈ $583), хотя UZS-объявление в разы дешевле. Кросс-валютный порядок цен
   бессмысленный, когда в выдаче смешаны USD и UZS (поиск по региону).

Решение по поведению согласовано с Team Lead (гибрид + нормализация по курсу).
Это затрагивает бизнес-правило промо-модели (ADR-0004) и поведение сортировки
(API-контракт §9), поэтому оформляется отдельным ADR, дополняющим ADR-0004.

## Decision

Поведение `GET /api/v1/search` зависит от того, выбрана ли сортировка ЯВНО:

- **«Рекомендуемые» (параметр `sort` отсутствует)** — без изменений: полный
  promotion-приоритет `effective_tier DESC, created_at DESC, id DESC` (ADR-0004).

- **Явный `sort`** (`price_asc`/`price_desc`/`area_desc`/`date_desc`) — **гибрид**:
  1. **Закреплённое промо («витрина»).** Топ-`PINNED_PROMO_COUNT` = **3** промо
     (по `tier_rank DESC, created_at DESC, id DESC`) прибиваются к началу 1-й
     страницы. Промо больше НЕ доминирует над всей выдачей.
  2. **Строгий поток.** Остальное строго по выбранному ключу
     (`<secondary> <dir>, id DESC`), без промо-приоритета. Закреплённые id
     исключены из потока на ВСЕХ страницах (без дублей). Keyset потока —
     2-кортежный `(<secondary>, id)`.
  3. **FX-нормализация цены.** Для `price_*` вторичный ключ нормализуется в USD:
     `CASE WHEN currency = 'UZS' THEN price / rate ELSE price END`, где `rate` —
     текущий курс ЦБУ (`1 USD = rate UZS`, последний по `fetched_at`, тот же
     источник, что `GET /api/v1/exchange-rate`). Курса нет → деградация к сырой
     цене (без падения). `area_desc`/`date_desc` нормализацию не используют.

`PINNED_PROMO_COUNT = 3` — константа в `SearchService`. Гео-эндпоинты
(`/search/radius|bounds|polygon|near-me`) не меняются (там нет пользовательского
сорта — всегда `date_desc`/distance с полным промо-приоритетом).

`total` неизменно = число совпадений по фильтру: закреплённые показываются один
раз на 1-й странице и исключены из потока, поэтому без двойного счёта. На 1-й
странице явной сортировки выдача = закреплённое промо (≤3) + страница потока,
т.е. может содержать до 3 элементов сверх `limit` — допустимо для keyset/
бесконечной прокрутки клиента.

## Consequences

Positive:
- «Сначала дешёвые/дорогие» работает интуитивно: цена решает порядок, реально
  самое дешёвое объявление — в начале потока.
- Кросс-валютная выдача упорядочена по реальной стоимости (USD-нормализация).
- Промо-модель сохраняет ценность: «витрина» из топ-3 промо остаётся на 1-й
  странице при любом явном сорте.
- Дефолт «Рекомендуемые» не изменился — обратная совместимость для тех, кто не
  трогает сорт.

Negative / trade-offs:
- Keyset строгого потока отдельный (2-кортежный) от дефолтного (3-кортежного с
  тиром) — две ветки в `search()`.
- FX-нормализация зависит от наличия строки курса; при пустой таблице
  `exchange_rates` `price_*` деградирует к сырой (кросс-валютно некорректной)
  цене. Курс обновляется джобой из ЦБУ (ADR-0093), поэтому в норме всегда есть.
- Курс между запросами страниц может измениться (обновление раз в сутки) —
  теоретический сдвиг keyset; на практике стабильно в рамках сессии.
- 1-я страница явного сорта может вернуть до `limit + 3` элементов.
