# ADR-0120 — Edit of an ACTIVE listing returns it to moderation

## Status

Accepted

## Date

2026-07-03

## Context

`PATCH /api/v1/listings/:id` (`ListingsService.update`) позволяет владельцу править
**своё** объявление в любом статусе кроме `DELETED`, включая уже опубликованное
`ACTIVE`. Правится широкий набор полей: цена/валюта, тип сделки и недвижимости,
площади, комнаты, санузлы, паркинг, удобства, этаж, год, адрес, город/район,
координаты, туры и авторский перевод (title/description/address_note/features_text).

До этого решения правка `ACTIVE`-объявления **не меняла статус** — изменённый
контент сразу оказывался в публичной выдаче **без повторной модерации**. Это
позволяло опубликовать «чистое» объявление, пройти модерацию, а затем подменить
текст/цену на произвольный — модерация фактически обходилась. В
`update-listing.dto.ts` это было отмечено как отложенная задача M5
(«возврат в модерацию после правки ACTIVE»).

Единственная существовавшая ветка повторной модерации касалась только `ARCHIVED`
(флаг `edited_since_hidden`, влияющий на smart-return при реактивации).

## Decision

**Правка `ACTIVE`-объявления возвращает его на повторную модерацию.** В
`ListingsService.update`, если текущий статус листинга `ACTIVE`, статус
переводится в `NEW` (объявление снова попадает в очередь модерации и уходит из
публичной выдачи до нового одобрения).

- `published_at` **не сбрасывается**: при повторном `APPROVE → ACTIVE`
  `ModerationService.changeStatus` сохраняет существующий `published_at`
  (`existing.publishedAt ?? new Date()`), поэтому дата первой публикации не теряется.
- Прочие статусы (`NEW`/`DRAFT`/`REJECTED`) при правке статус не меняют; `ARCHIVED`
  сохраняет прежнее поведение (`edited_since_hidden = true`).
- Гейт полноты переводов при повторном `APPROVE` остаётся прежним (ADR-0091):
  строки uz/ru/en уже существуют, поэтому публикация не блокируется, но объявление
  проходит человеческую перепроверку. Авто-детект «протухшего» машинного перевода
  после правки оригинала — вне scope этого ADR (отдельная задача).

## Consequences

Positive:

- Изменённый контент опубликованного объявления не остаётся в выдаче без проверки —
  модерация больше не обходится правкой.
- Минимальное изменение: одна ветка в `update()`, поведение остальных статусов не
  затронуто.
- Дата первой публикации сохраняется благодаря существующей логике `changeStatus`.

Negative / trade-offs:

- Любая правка `ACTIVE` (даже мелкая — этаж, год, одно удобство) скрывает объявление
  до повторного одобрения. Это осознанный выбор Team Lead в пользу контроля над
  гранулярностью; дифференциация «существенных» правок — возможная будущая доработка.
- Растёт нагрузка на очередь модерации при частых правках активных объявлений.
- Машинные переводы после правки оригинала могут остаться устаревшими до момента,
  когда модератор их перегенерирует вручную (ADR-0091).

## Update (2026-07-23) — REJECTED re-moderation, content-gate & OWNER_EDIT log

Расширение исходного решения по итогам ревью Team Lead:

1. **`REJECTED` тоже возвращается в `NEW` при правке.** Раньше отклонённое
   модератором объявление после исправления (напр. завышенной цены) **оставалось
   `REJECTED`** и больше не попадало в очередь — правка «висела» отклонённой
   навсегда. Теперь правка `ACTIVE` **или** `REJECTED` возвращает в `NEW`.
   `DRAFT` по-прежнему не ре-модерируется (авторского черновика в системе нет —
   `DRAFT` возникает только через `SEND_TO_DRAFT`; отдельное решение Team Lead).

2. **Гейт по реальному изменению контента.** Возврат в `NEW` происходит, только
   если действительно изменилось контентное поле (цена, тип, площади, комнаты,
   адрес, координаты, удобства, авторский перевод и т.п.). «Тихое» сохранение без
   изменений или правка **одних лишь окон туров** (`tours_enabled`/`tour_windows` —
   расписание, не контент) статус не меняет. Это снимает часть trade-offّа из
   раздела Consequences (мелкие/нулевые правки больше не скрывают объявление).

3. **Лог `OWNER_EDIT` в таймлайн модерации.** При возврате в очередь в
   `moderation_logs` пишется системная запись (новое значение enum
   `ModerationAction.OWNER_EDIT`, `moderator_id = null`, `old→new = <статус>→NEW`),
   где `reason` — человекочитаемый список изменённых полей (напр. «Изменено: цена
   4500000.00 UZS → 4300000.00 UZS, описание»). Модератор видит её в «Истории
   модерации» (`GET /admin/listings/:id/moderation-logs`) и сразу понимает, почему
   объявление вернулось. `ModerateListingDto` (решение модератора) значение
   `OWNER_EDIT` **не принимает** — оно только системное/read-only.

   Замечание: правка фотографий идёт отдельным media-эндпоинтом и в этот триггер
   пока не попадает — возможная будущая доработка.
