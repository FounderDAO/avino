# ADR-0152 — Сброс RTK Query-кэша при смене личности

## Status

Accepted

## Date

2026-07-22

## Context

Заказчик залогинился под несколькими аккаунтами по очереди (A → B → C). После
смены аккаунта раздел «Мои объявления» показывал объявления **предыдущего**
пользователя (объявления аккаунта A в кабинете B). Первое подозрение — «токен
не меняется».

Диагностика показала, что токен как раз меняется корректно: `verifyOtp` /
`googleLogin` / `appleLogin` через `setCredentials` перезаписывают access
(в памяти Redux) и refresh (localStorage), а `baseQuery` подставляет свежий
Bearer. Настоящая причина — **stale-кэш RTK Query**:

- Кэш RTK Query ключуется по `(endpointName + args)` и **не учитывает
  пользователя**. `getMyListings({status,page,limit})` для аккаунта A и B — это
  один и тот же cache-key.
- Ни вход (`verifyOtp` → `invalidatesTags: ['Auth','User']`), ни выход
  (`logout` → `invalidatesTags: ['Auth','User']`) не инвалидировали тег
  `Listing`, а `baseApi.util.resetApiState()` не вызывался нигде.
- Итог: после logout+login кэш прежнего пользователя оставался жить и всплывал
  в UI до рефетча. Помимо путаницы это утечка данных между аккаунтами на одном
  устройстве.

Тот же архитектурный дефект присутствовал в админке (`apps/web`): login/logout
инвалидировали только `Auth`, `resetApiState` не вызывался. Риск там ниже —
большинство admin-данных общие для всех модераторов (`Admin`-теги), но
персонально-специфичный `getMe` (профиль/роли) мог мигать данными прежнего
админа.

## Decision

На **смену личности** сбрасывать весь api-кэш через
`baseApi.util.resetApiState()`, реализованный отдельным
`createListenerMiddleware` (`store/identityResetListener.ts`), подключённым в
store через `.prepend(...)`.

Выбран `resetApiState` (немедленное удаление данных), а **не** `invalidateTags`:
последний оставляет старые данные видимыми до завершения рефетча (окно утечки
сохранялось бы), и не чистит записи, на которые в момент смены никто не
подписан. Активные подписки (напр. `getMe` в `SessionBootstrap`) после сброса
автоматически рефетчатся уже с новым токеном.

Смена личности отделяется от **ротации токена** (тот же пользователь — сбрасывать
кэш на каждой ротации нельзя, иначе рефетч всего на каждой холодной загрузке,
ADR-0142):

- **apps/client** — matcher `isAnyOf(setCredentials, clearCredentials)`; ротация
  переиздаёт креды тем же `setCredentials`, но **без** `user`, поэтому эффект
  игнорирует случай `action.payload.user === undefined`.
- **apps/web** — matcher `isAnyOf(setCredentials, logOut)`; ротация здесь —
  отдельный action `setTokens`, который просто не матчится (проверка на `user`
  не нужна).

Безопасность для login-флоу: все входы используют `.unwrap()` (значение из
промиса, не из tracked-состояния мутации), поэтому сброс api-кэша, обнуляющий
состояние самой login-мутации, вход не ломает.

## Consequences

Positive:
- Данные одного пользователя больше не всплывают у другого после смены аккаунта;
  утечка между аккаунтами на одном устройстве закрыта.
- Единый предсказуемый паттерн для обоих фронтов; ротация токена кэш не трогает.

Negative / trade-offs:
- На каждый login/logout — полный сброс кэша и рефетч активных подписок (в т.ч.
  при релогине того же пользователя). Цена приемлема: событие редкое, рефетч
  атомарный.
- Первый вход гостя (guest → A) тоже сбрасывает кэш публичных данных (search и
  т.п.) — семантически корректно (личность сменилась), лишний рефетч разовый.
