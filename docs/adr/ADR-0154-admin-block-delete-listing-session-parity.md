# ADR-0154 — Админ-блокировка и удаление аккаунта: паритет с self-service

## Status

Accepted

## Date

2026-07-23

## Context

В админ-карточке пользователя (`apps/web` → `/admin/users/[id]`, карточка
«Действия») есть кнопки «Заблокировать» и «Удалить аккаунт». Обе были подключены
к `PATCH /api/v1/admin/users/:id`, но серверный `AdminUsersService.updateStatus`
делал **только** смену `users.status` (+ `deleted_at` для DELETED) и запись
`audit_logs(ADMIN_USER_UPDATE)`. Причина вводилась через `window.prompt`.

При сравнении с недавним self-service удалением (`DELETE /users/me`, ADR-0140/#457,
`UsersService.deleteMe`) вскрылись пробелы:

- **Блокировка** запрещала новый вход (`auth.service` кидает `USER_BLOCKED`), но
  **объявления заблокированного оставались в публичной выдаче** — их никто не
  снимал.
- **Удаление** блокировало вход/refresh, но **объявления оставались LIVE** на
  портале, а refresh-токены не отзывались явно. Админское удаление было слабее
  пользовательского самоудаления (которое снимает объявления по `ownerId` и
  отзывает все токены).
- `GET /auth/me` пускал `BLOCKED` (фильтр `status: { not: DELETED }`) — юзер с
  ещё живым access-токеном продолжал получать профиль.

Открытые вопросы:

1. **Как прятать объявления заблокированного и как возвращать их при
   разблокировке** (блокировка обратима, в отличие от удаления). В `ListingStatus`
   нет статуса «скрыто админом», а публичность везде завязана на единый гейт
   `status = ACTIVE`; `/search` — сырой SQL по `listings` без join на `users`,
   публичных read-путей много (search, листинг по id, by-ref, og:image, sitemap,
   объявления агента, home).
2. **Нужно ли чинить refresh-ротацию.** Первоначально предполагалась дыра
   «заблокированный бесконечно рефрешит».

## Decision

**Довести админские block/delete до паритета с self-service, всё атомарно в одной
`$transaction`; видимость объявлений держать на существующем гейте `status`
(мутация статуса), а не на фильтре по `owner.status`.**

Мутация статуса переиспользует единственный существующий гейт видимости
(`status = ACTIVE`) во всех публичных путях — ноль изменений в запросах и в
горячем гео-SQL. Альтернатива (фильтр `owner.status = ACTIVE` во всех запросах)
отклонена: пришлось бы тронуть ~7 read-путей включая сырой SQL, и пропуск любого
означает утечку объявления заблокированного по прямой ссылке.

`AdminUsersService.updateStatus` ветвится по целевому статусу:

- **BLOCKED** — собрать id ACTIVE-объявлений владельца → `user.status = BLOCKED`
  (`deleted_at = null`) → `listing.updateMany(ACTIVE → ARCHIVED)` →
  `refreshToken.updateMany(revoke all active)` → audit `ADMIN_USER_UPDATE` с
  `metadata.archived_listing_ids` (для обратимости).
- **ACTIVE (разблокировка)** — прочитать последнюю BLOCKED-запись аудита
  (JSON-path `metadata.new_status = BLOCKED`) → взять `archived_listing_ids` →
  `user.status = ACTIVE` → вернуть в `ACTIVE` **только** те id, что всё ещё
  `ARCHIVED` и принадлежат владельцу (то, что владелец сам заархивировал за время
  блокировки, не воскрешаем) → audit с `restored_listing_ids`. Обратимость — без
  изменения схемы БД, через метаданные аудита.
- **DELETED** — паритет с `UsersService.deleteMe`: `user.status = DELETED`
  (`deleted_at = now`) → `listing.updateMany(not DELETED → DELETED)` →
  `refreshToken.updateMany(revoke all active)` → audit с `reason`.

**Refresh-дыры не оказалось:** `TokenService.rotateSession` уже отклоняет любой
не-ACTIVE аккаунт (`user.status !== ACTIVE`) с отзывом всей family (покрыто
существующим тестом). Отдельно закрыт меньший зазор: `GET /auth/me` теперь
фильтрует `status: { notIn: [DELETED, BLOCKED] }` → BLOCKED с живым
access-токеном получает 401 и разлогинивается на следующем вызове. Login-путь
(`resolveUser`) не тронут — там уже есть явная проверка `USER_BLOCKED`.

**UX:** `window.prompt` заменён на `UserStatusReasonModal` (apps/web) — две
конфигурации (block/delete) с обязательным полем причины и danger-кнопкой, без
типизированного слова-подтверждения. Разблокировка осталась прямым действием без
модалки.

Контракт `UpdateAdminUserDto` (`status` + `reason`) и форма ответа
(`AdminUserDetail`) не изменились; новые поля — только во внутреннем
`audit_logs.metadata` → регенерация OpenAPI не требуется.

**Дополнение (2026-07-24): DELETED — терминальный статус в админ-UI.**

Прод показал 500 на «Разблокировать» для удалённого аккаунта: кнопка была
бинарной (`active ? Заблокировать : Разблокировать`) и предлагала перевести
DELETED → ACTIVE. Уникальность контактов частичная
(`uniq_users_phone_active`/`uniq_users_email_active`, `WHERE status <> 'DELETED'`,
ADR-0152 self-delete): пока строка удалена, тот же телефон легально занимает
новая регистрация, а «воскрешение» упирается в индекс → Prisma `P2002` → 500.

Поэтому:

- **apps/web** — при `status = deleted` блок «Действия» не показывает кнопок
  вовсе (ни разблокировки, ни повторного удаления), только пояснение: аккаунт
  удалён, восстановление не поддерживается. Восстановление и не сработало бы
  по смыслу: `applyDelete` перевёл объявления в `DELETED`, а `applyUnblock`
  возвращает только `ARCHIVED` из BLOCKED-аудита.
- **apps/api** — `updateStatus` ловит `P2002` и отдаёт `409 CONTACT_TAKEN`
  («phone/email принадлежит другому активному аккаунту») вместо 500. Ветка
  BLOCKED → ACTIVE конфликта дать не может (BLOCKED уже в индексе), так что
  штатная разблокировка не затронута.

## Consequences

- Блокировка теперь реально скрывает контент нарушителя и завершает сессии;
  разблокировка полностью обратима (возврат ровно спрятанного).
- Админское удаление больше не оставляет «осиротевшие» LIVE-объявления.
- Обратимость блокировки опирается на метаданные аудита: если BLOCKED-запись
  аудита отсутствует/повреждена, разблокировка просто не восстанавливает
  объявления (fail-safe, без исключений).
- **Принятое ограничение:** access-токен живёт до своего TTL (~15 мин) после
  блокировки/удаления — `JwtAuthGuard` не сверяет БД на каждый запрос (идентично
  self-delete). Не чинится здесь; потребовало бы денилиста токенов или DB-проверки
  на каждый запрос.
- **Принятое ограничение:** soft-delete необратим и в админке тоже — вернуть
  удалённый аккаунт нельзя (контакты могли уйти новой регистрации, объявления
  уже DELETED). Полноценное восстановление потребовало бы разрешения конфликтов
  контактов и отдельного флага «удалено админом vs самим юзером».
- Тесты (JEST, `admin-users.service.spec.ts`): block (ARCHIVED + revoke + audit
  ids), unblock (точный возврат, самостоятельно заархивированные не воскрешаются),
  delete (паритет), P2002 → `409 CONTACT_TAKEN`. Refresh-BLOCKED уже покрыт
  `token.service.spec.ts`.
