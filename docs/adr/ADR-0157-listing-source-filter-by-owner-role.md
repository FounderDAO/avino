# ADR-0157 — Фильтр «Собственник / Агентство» по роли владельца, а не по agency_id

## Status

Accepted (уточняет реализацию listing_source из TASK-Zillow Phase 1)

## Date

2026-07-24

## Context

Фильтр поиска **«Собственник / Агентство»** (`?listing_source=OWNER|AGENCY`,
чипы в `FiltersPanel`) на сервере (`SearchService.buildWhereSql`) различал
продавца по колонке `listings.agency_id`:

```
OWNER  → agency_id IS NULL
AGENCY → agency_id IS NOT NULL
```

Проблема: **`agency_id` — колонка-заглушка, которая никогда не заполняется.**
Агентства как отдельная сущность в системе ещё не заведены (`schema.prisma`:
«agencies/cities/districts ещё не созданы» — колонки заведены как UUID-скаляры
без FK-таблиц). Форма создания объявления `agency_id` не отправляет, сид его не
ставит; единственная запись — admin-update DTO, для которого нет UI. Итог на
реальных данных:

- **OWNER** возвращает **все** объявления (у всех `agency_id IS NULL`);
- **AGENCY** возвращает **ноль** объявлений.

То есть фильтр не работает — обе ветки бесполезны.

Между тем **весь остальной код различает тип продавца по РОЛИ владельца**:
`ListingsService.buildContact` (contact-блок, бейджи карточки) —
`AGENCY → «agency», AGENT → «agent», иначе «owner»` («pro = agent/agency»).
Роли `AGENT`/`AGENCY` выдаёт флоу «Стать агентом» (ADR-0140). Фильтр был
рассинхронизирован с доменной моделью.

Продуктовое решение (Team Lead): пока **два типа продавца** — «Собственник»
(OWNER) и «Агентство» (AGENT + AGENCY как единый тип «профессионал»).

## Decision

1. **Фильтр `listing_source` определяет тип продавца по роли владельца**, а не
   по `agency_id`. В `SearchService.buildWhereSql` условие переписано на
   коррелированный подзапрос:

   ```sql
   EXISTS (
     SELECT 1 FROM user_roles ur
     JOIN roles r ON r.id = ur.role_id
     WHERE ur.user_id = listings.owner_id
       AND r.code IN ('AGENT', 'AGENCY')
   )
   ```

   - `AGENCY` → `EXISTS (...)` — владелец с ролью `AGENT` **или** `AGENCY`;
   - `OWNER`  → `NOT EXISTS (...)` — владелец без агентских ролей.

   Как и раньше, `[OWNER, AGENCY]` (оба чипа) → фильтр не применяется.

2. **Единый тип «Агентство» = AGENT ∪ AGENCY.** Согласуется с `buildContact`
   («pro = agent/agency»). Разделение частных агентов и агентств отложено до
   появления сущности агентств.

3. **`agency_id` остаётся мёртвой колонкой-заглушкой** (не удаляется — вне
   рамок задачи; заведётся при реальной модели агентств).

Правка в одном месте (`buildWhereSql`) покрывает все варианты выдачи —
дефолтную (keyset), явную сортировку (explicit-sort) и гео (bounds) — так как
все они строят WHERE через этот метод. Внешний запрос — bare `FROM listings`
(без алиасов и join), поэтому коррелированная ссылка `listings.owner_id`
однозначна.

## Consequences

- Фильтр «Собственник / Агентство» начинает работать на реальных данных;
  результат совпадает с бейджем продавца на карточке (единый источник истины —
  роль владельца).
- Небольшой оверхед на подзапрос по `user_roles` (индексы `user_roles(user_id)`
  и `roles(code UNIQUE)` уже есть) — только когда чип выбран.
- Int-тест переписан с ролевой модели: старый «проходил» лишь потому, что руками
  проставлял `agency_id` на фикстурах (данные, которых в проде нет) — классика
  «тест зелёный, прод сломан». Теперь land/comm принадлежат владельцу с ролью
  `AGENT`, apt/house — частному.
- Клиент (`FiltersPanel`/`FilterBar`/`search/page.tsx`) не менялся — цепочка
  `чип → ?listing_source → API` была корректна; баг чисто серверный.

## Alternatives considered

- **Заполнять `agency_id` при создании** (backfill + запись из формы) — требует
  завести сущность агентств и связать пользователей с ними; преждевременно, роль
  владельца уже несёт нужную семантику.
- **Разделить AGENT и AGENCY на два чипа** — отклонено: продуктово нужен один
  тип «Агентство» до появления модели агентств.
