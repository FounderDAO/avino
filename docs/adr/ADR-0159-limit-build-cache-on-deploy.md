# ADR-0159 — Ограничение кэша сборки при деплое

## Status

Accepted

## Date

2026-08-15

## Context

Аудит прод-сервера (`157.180.96.205`, диск 437 ГБ) показал перекос:

| Категория | Занято |
|---|---|
| Images | 4.45 ГБ |
| Containers | 1.04 ГБ |
| Local Volumes | 121 МБ |
| **Build Cache** | **85.22 ГБ** (76.97 ГБ подлежит очистке) |

Кэш сборки — это практически весь занятый диск: 85 ГБ против 5.6 ГБ полезного
содержимого. Причина в том, что образы собираются прямо на VPS
(`docker compose up -d --build` в `deploy/deploy.sh`), и каждая сборка оставляет
слои.

Первая гипотеза «у сборщика нет GC» **не подтвердилась** — проверка
`docker buildx inspect default` показала, что политики есть и включены:

```
rule#1/2/3:  Reserved Space 40.98GiB | Max Used Space 326GiB | Min Free Space 81.96GiB
rule#0:      type==source.local,cachemount,git — Keep 48h, Max 5.66GiB
```

BuildKit считает их от размера диска (~75% потолок, ~20% неснижаемый свободный
остаток, ~10% резерв). То есть бесконечно кэш не растёт — но потолок рассчитан
на машину, где Docker единственный жилец: уборка включится, когда свободного
останется меньше ~82 ГиБ, а до тех пор кэшу разрешено вырасти ещё на ~240 ГБ.

Для прод-сервера это слишком поздно: к моменту срабатывания встроенной защиты
кто-то уже будет разбираться, почему кончается место. При этом ценность кэша
здесь невелика — деплой нечастый, а `Keep Duration` основного правила 60 дней,
то есть слои живут долго и в большинстве протухшие.

Прочее на сервере здорово и в лечении не нуждается: логи контейнеров занимают
10 МБ, лимит логов стоит и в `/etc/docker/daemon.json` (`20m`×`5`), и в
`docker-compose.prod.yml`; база 25 МБ без следов раздутия.

## Decision

В `deploy/deploy.sh` и `deploy/deploy-staging.sh` после health-check добавлен шаг:

```bash
docker builder prune --force --max-used-space "${BUILD_CACHE_MAX_SPACE:-20GB}" \
  || printf '⚠ очистка кэша сборки не удалась — деплой не затронут\n'
```

Потолок 20 ГБ — с запасом к 4.45 ГБ образов, сборки остаются быстрыми.
Переопределяется переменной `BUILD_CACHE_MAX_SPACE`.

Четыре решения по месту:

1. **`docker builder prune`, а не `builder.gc` в `/etc/docker/daemon.json`.**
   Секция `builder` не поддерживает live-reload, `Live Restore` на сервере
   выключен — применение через daemon.json требовало бы рестарта демона, то есть
   простоя контейнеров при каждом деплое.
2. **После health-check, а не до сборки.** Провалившийся деплой сохраняет кэш
   целиком, что нужно для быстрого отката; слои только что собранных образов
   чистку переживают, срезается лишь старое.
3. **Это действительно предел, а не разовая уборка.** Кэш растёт только во время
   сборки, а сборка бывает только здесь — очистка сразу после неё замыкает цикл,
   между деплоями кэшу расти неоткуда.
4. **best-effort.** Сбой очистки не должен ронять уже успешный деплой.

`deploy/deploy-client.sh` не тронут — он не собирает образы.

## Alternatives

- **`builder.gc` в `daemon.json`** — см. п.1 выше: простой при каждом деплое.
- **Cron с `docker builder prune`** — отдельная сущность, которая может
  сработать в момент сборки и срезать нужный слой; привязка к деплою точнее.
- **Разовая ручная чистка** — лечит симптом один раз, через полгода вернётся.
- **Вынести сборку в CI (образы в GHCR + `docker compose pull` на сервере)** —
  правильное решение в корне, кэш на VPS не появлялся бы вовсе. Записано в
  `docs/DevOps.md` п.9 как «CD-минимум» и остаётся открытым: эта правка не
  отменяет его, а закрывает дыру до его реализации.

## Consequences

Кэш сборки ограничен 20 ГБ. Первый деплой после этой правки срежет ~65 ГБ и
займёт больше обычного; последующие — штатно.

Сборки могут стать чуть медленнее, если между деплоями прошло много времени и
часть слоёв срезана. Компромисс осознанный: 20 ГБ достаточно для переиспользования
слоёв текущего образа.

Ограничение действует **только при деплое**. Если сборки запускать на сервере
руками мимо `deploy.sh`, кэш снова растёт до встроенного потолка BuildKit.

## Verification

Флаг проверен на живом сервере заведомо большим значением, которое ничего не
удаляет:

```bash
$ docker builder prune --force --max-used-space 500GB
Total:  0B
$ docker buildx du | tail -1
Total:  85.22GB     # не изменился
```

Синтаксис обоих скриптов: `bash -n deploy/deploy.sh deploy/deploy-staging.sh` — чисто.

После первого деплоя проверять так:

```bash
docker buildx du | tail -3     # Total должен быть ≤ 20GB
docker system df               # Build Cache в общей картине
```
