# ADR-0167 — Автовыход после 7 дней бездействия

## Status

Accepted (меняет TTL из ADR-0014; механика ротации — ADR-0010, cookie — ADR-0153)

## Date

2026-10-03

## Context

Клиент (баг-репорт 1, п. 3) попросил автоматически разлогинивать пользователя.
Сейчас access-токен живёт 15 минут, refresh — 30 дней. Каждая ротация на
`POST /auth/refresh` создаёт новый refresh с `expires_at = now + JWT_REFRESH_TTL`
и заново ставит cookie `avino_rt` с тем же Max-Age, то есть срок скользящий:
активный пользователь не выходит никогда, неактивный выходит через 30 дней.
Клиент выбрал правило «выход после 1 недели бездействия».

## Decision

1. `JWT_REFRESH_TTL` по умолчанию — `604800` (7 дней) вместо `2592000`.
   Дефолт Max-Age cookie (`AUTH_COOKIE_MAX_AGE_SEC`) следует за ним.
2. Механика не меняется. Скользящий срок уже даёт нужное поведение: «бездействие»
   = нет ни одного запроса, вызвавшего ротацию (открытие сайта делает пробный
   silent-refresh, дальше ротация примерно раз в 15 минут при запросах).
   Абсолютного предела сессии нет — активный пользователь остаётся в аккаунте.
3. По истечении срока `/auth/refresh` отвечает `401 TOKEN_EXPIRED`, клиент
   очищает сессию (гость), админка уходит на страницу входа.

## Consequences

- Точность — до 15 минут (TTL access-токена): последняя ротация могла быть
  чуть раньше последнего действия.
- Уже выданные refresh-токены сохраняют прежний `expires_at` (до 30 дней) до
  своей следующей ротации; после неё действует новый срок. Массово не
  отзываем — никого не разлогиниваем при выкатке.
- В окружениях, где `JWT_REFRESH_TTL` / `AUTH_COOKIE_MAX_AGE_SEC` заданы явно
  (prod/staging `.env`), значения нужно поменять там же — дефолт кода их не
  перекрывает.
- Мобильное приложение использует тот же refresh — правило действует и там.
