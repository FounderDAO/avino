**Дата:** 2026-06-28
**Статус:** утверждён к планированию

Два независимых улучшения. Поставляются отдельно (разные app-папки → разные PR):

- **Фича 1** — только `apps/client` (frontend).
- **Фича 2** — только `apps/api` (backend).

## Фича 1 — «Это ваше объявление» на detail-странице

### Цель
Когда залогиненный пользователь открывает **своё** объявление, вместо блока «контакты продавца / чат» показать плашку «Это ваше объявление» с быстрым переходом к управлению.

### Скоуп
- Только detail-страница (`/{locale}/listing/[id]`). Бейдж «Ваше» на карточках в ленте/поиске — **вне скоупа**, отдельный follow-up (требует прокинуть `owner_id` в ответ `/search` на бэкенде).
- Только `apps/client`. Бэкенд не трогаем — `owner_id` уже приходит в ответе detail.

### Поток данных
1. Ответ detail (`ApiListingDetail`) уже содержит `owner_id` (см. `apps/client/src/lib/api/listings.ts`), но он не прокидывается в UI-тип `Listing`.
   - Добавить `ownerId?: string` в тип `Listing` (`apps/client/src/lib/mock/types.ts`).
   - В `mapListing()` (`apps/client/src/lib/api/listings.ts`) заполнить `ownerId: detail?.owner_id`.
2. В `ContactCard.tsx` (`apps/client/src/features/detail/`):
   - Прочитать текущего пользователя: `const currentUser = useAppSelector(selectCurrentUser)`.
   - `const isOwner = isAuthenticated && Boolean(currentUser?.id) && currentUser?.id === listing.ownerId`.
   - `isOwner === true` → рендерить «владельческий» вид вместо «показать телефон / написать».

### Владельческий вид (плашка + управление)
Заменяет аватар+контакты продавца и кнопки «показать телефон» / «написать»:
- Заголовок-плашка: «Это ваше объявление».
- Кнопка primary «Редактировать» → `/{locale}/sell/${listing.id}/edit` (существующий маршрут редактирования).
- Ссылка/кнопка secondary «Мои объявления» → `/{locale}/account/my-listings` (там уже есть управление статусами: скрыть / продано / сдано через `useSetMyListingStatusMutation`). На detail статусы **не дублируем**.
- Кнопку «Поделиться» оставляем (полезна и владельцу).

### i18n
Новые ключи в namespace `listing.contact.*`, файлы `apps/client/messages/{ru,uz,en}.json`:
- `ownerNotice` — «Это ваше объявление»
- `editListing` — «Редактировать»
- `manageListings` — «Мои объявления»

### Граничные случаи
- `isOwner` вычисляется после гидратации (текущий пользователь — в redux на клиенте, `owner_id` — из SSR-пропа). Возможен короткий «промельк» контактной карточки до плашки. Приемлемо — то же поведение, что у кнопки «написать», которая уже гейтится на авторизацию.
- Неавторизованный пользователь / чужое объявление → обычный контактный вид (без изменений).
- `listing.ownerId` отсутствует (старый кэш/ответ без поля) → `isOwner = false`, обычный вид.

### Тестирование
- Юнит/компонентный тест `ContactCard`: рендерит владельческий вид при `currentUser.id === listing.ownerId`; рендерит обычный контактный вид иначе (не-владелец, аноним, отсутствует `ownerId`).
- Проверить наличие новых i18n-ключей во всех трёх локалях вручную (mocked next-intl скрывает отсутствующие ключи — известная гоча проекта).
- Lint + build `apps/client`.

## Фича 2 — Обход OTP для номера-ревьювера (env-gated)

### Цель
Аккаунт `+998902793100` для iOS/Android-ревьюверов App Store / Google Play входит **с любым 6-значным кодом**, без отправки SMS. Включается env-флагом (по умолчанию ВЫКЛ), работает на staging и prod. Только указанный номер, обычная роль USER.

### Скоуп
- Только `apps/api`. Без миграций БД.

### Выбранный подход: env-allowlist в auth/otp-сервисах
Следует существующему паттерну фича-флагов (`OTP_TELEGRAM_DELIVERY`, `TELEGRAM_INCLUDE_OTP_CODE`).

**Конфигурация** (`apps/api/src/config/configuration.ts`, namespace через `registerAs`; опциональные поля в `env.validation.ts`):
- `OTP_BYPASS_ENABLED` — boolean, default `false`.
- `OTP_BYPASS_PHONES` — строка CSV номеров в E.164 (например `+998902793100`). Парсится в массив нормализованных номеров.

Хелпер `isBypassPhone(destination, channel)`: возвращает `true`, только если флаг включён, канал `SMS`, и нормализованный `destination` входит в allowlist.

**Request-сторона** — `otp.service.ts` → `requestOtp`:
- Если `isBypassPhone(...)` → **короткое замыкание в начале метода, до проверки «SMS включён»**: не генерируем код, ничего не шлём (ни Eskiz, ни Telegram, ни запись OtpCode не обязательна), возвращаем обычный success-ответ запроса OTP.
- Эффект: запрос кода для номера-ревьювера успешен даже при выключенном Eskiz/SMS.

**Verify-сторона** — `auth.service.ts` → `verifyOtp`:
- Если `isBypassPhone(...)` → пропускаем поиск последнего OTP и сравнение хэша; принимаем любой код, прошедший валидацию DTO (`@Length(6,6)` — ровно 6 цифр).
- Дальше — штатный путь: `resolveUser(SMS, destination)` (найти-или-создать пользователя с ролью USER), `lastLoginAt`, выдача access/refresh токенов как обычно.

### Безопасность и границы
- Скоуп — ровно номера из `OTP_BYPASS_PHONES`. Пустой список или `OTP_BYPASS_ENABLED=false` → поведение не меняется.
- Рейт-лимит (`@Throttle 10/min`) и нормализацию E.164 **оставляем** — не ослабляем сверх необходимого.
- Bypass работает только для канала `SMS` (email-канал не затрагивается).
- Аккаунт ревьювера держать как обычный USER. **Операционное предупреждение:** не выдавать этому аккаунту admin-роль в БД — иначе обход = вход под admin для любого, кто знает номер.
- Существующие Telegram-алерты логина продолжают работать без изменений.

### Граничные случаи
- Флаг ВКЛ, но номер не в списке → обычный OTP-поток.
- Канал EMAIL для номера из списка → обычный поток (bypass не применяется).
- Невалидный E.164 в `OTP_BYPASS_PHONES` → игнорируется при парсинге (не попадает в allowlist).

### Тестирование
- Юнит-тесты `auth.service` / `otp.service`:
  - bypass-номер при `OTP_BYPASS_ENABLED=true`: `requestOtp` не дёргает SMS-сервис и не падает при выключенном SMS; `verifyOtp` принимает произвольный 6-значный код и возвращает токены.
  - тот же номер при `OTP_BYPASS_ENABLED=false`: обычный поток (request шлёт/готовит код, verify требует корректный код).
  - обычный номер при включённом флаге: не затронут.
- Lint + build `apps/api`. Если правок схемы Prisma нет — `prisma generate` не требуется.

### Прод-развёртывание (TODO вне кода)
- Прописать в серверные `.env` (staging + prod): `OTP_BYPASS_ENABLED=true`, `OTP_BYPASS_PHONES=+998902793100`.
- Пересоздать api-контейнер (`up -d --force-recreate api`, не restart).
