# Дизайн: нормализация адреса объявления + ru/en версии по координатам

Дата: 2026-07-13. Статус: одобрен Tommy (чат), реализация в 2 PR.

## Проблема

1. В `listings.address` попадает сырая строка и ломает вёрстку карточек:
   - Yandex Suggest в визарде: `AddressStep.handleSelect` сохраняет `displayName` как есть —
     «город Ташкент, Мирзо-Улугбек, ул. Бабура, 13, Мирзо-Улугбек р-н, Ташкент»;
   - реверс-геокод при перетаскивании точки (`geocode.ts getAddressLine()`): «Узбекистан, Ташкент, …»;
   - сиды (`seed-all.cjs:514`): префикс `regions.name_ru` = «город Ташкент».
2. Адрес хранится только на русском: при переключении локали en/uz не меняется.

## Целевой формат

- ru: `Ташкент, Мирзо-Улугбек, ул. Бабура, 13`
- en: `Tashkent, Mirzo-Ulugbek, Bobur ko'chasi, 13`
- uz: перевода нет — показываем ru (осознанное решение Tommy, Яндекс uz не поддерживает).

Составные части: `{locality}, {district}, {street}, {house}` — без страны, без «город »,
без дублей района/города в хвосте.

## Решение

### PR-1 — apps/api: AddressResolver + нормализация + backfill

1. **Миграция**: `listings.address_en VARCHAR NULL`.
   - Почему НЕ `listing_translations.address`: в `ListingTranslation` поля `title`+`source`
     NOT NULL, а EN-строка создаётся лишь при модерации автопереводчиком — upsert
     «только адрес» при создании объявления потребовал бы фиктивный title и мешал бы
     семантике `is_auto_translated`. Адрес — машинная геодата, живёт в `listings`.
2. **AddressResolver** (новый модуль `apps/api/src/geocoding/`):
   - вход: `lat`, `lng`, `districtId?`;
   - два параллельных запроса к HTTP Геокодеру `https://geocode-maps.yandex.ru/1.x/`
     (`sco=longlat`, `kind=house`, `format=json`, `results=1`, `lang=ru_RU` / `lang=en_US`);
   - ключ: env `YANDEX_MAPS_API_KEY` (уже объявлен в `.env`, значение = ключ JS API —
     entitlement **проверен curl'ом 2026-07-13, оба языка работают**);
   - парсим **структурные** `Address.Components` (kind: locality, street, house) — строку
     `text` не режем;
   - район подставляем из НАШЕЙ таблицы `districts` по `district_id`
     (`name_ru`/`name_en` — консистентно с фильтрами и уже трёхъязычно); нет district_id —
     компонент опускается;
   - словарь сокращений для ru-улиц: «улица »→«ул. », «проспект »→«просп. »,
     «переулок »→«пер. », «шоссе » остаётся; en не трогаем;
   - таймаут ~3s, ошибки не пробрасываются (best-effort).
3. **Строковый фолбэк-нормализатор** `normalizeAddress(raw: string): string` (чистая функция,
   юнит-тесты): split по «, », выбросить «Узбекистан»/«Uzbekistan», срезать префиксы
   «город »/«г. », выбросить хвостовые части, дублирующие уже встреченные (нормализация
   для сравнения: lower, ё→е, срез « р-н»/« район»/«-ский район», «district»). Применяется
   всегда к присланному `dto.address`, даже когда геокодер недоступен.
4. **Хуки в ListingsService**:
   - `create`: если есть координаты — синхронный best-effort резолв (≤3s): ru → `address`,
     en → `address_en`; геокодер молчит/нет ключа → `address = normalizeAddress(dto.address)`,
     `address_en = null`;
   - `update`: то же, если изменились `latitude`/`longitude`/`address`.
5. **Backfill-скрипт** (`apps/api/prisma/` или scripts): все не-DELETED объявления с
   координатами → резолв → update `address`/`address_en`; без координат → только
   `normalizeAddress`. Идемпотентный, пауза между запросами (лимиты бесплатного тарифа).
6. **Сиды**: `seed-all.cjs` — убрать «город » из собираемого адреса (генерить целевой формат
   сразу; `address_en` в сиде собрать из `name_en` района + транслит улицы не требуется —
   допустимо оставить null → фолбэк ru).

### PR-2 — выдача и клиент

7. **API-выдача**: везде, где отдаётся `address` и известен язык запроса (search list,
   detail, кластера-превью, og-контексты), резолвить: `lang === EN ? (address_en ?? address)
   : address`. Механизм выбора языка тот же, что для `title` (langParam / Accept-Language).
8. **Клиент**: PropertyCard, detail, ShareButton, og — показывают то, что пришло с сервера;
   изменения минимальны (проверка точек показа + тесты).

## Не входит в объём

- Перевод адреса на uz (МТ) — отложен; слот готов (та же схема, колонка `address_uz` при надобности).
- Изменение семантики `q` ILIKE-поиска: канон `listings.address` остаётся русским.

## Риски

- Качество en-геокода — транслит («Seul koʻchasi»), не литературный перевод; принято.
- Лимиты HTTP Геокодера на backfill — скрипт с паузами, объём в staging мал.
- Проверка ключа выполнена: `curl …lang=ru_RU|en_US` → 200, компоненты полные.

## Верификация

- Юнит: `normalizeAddress` (кейсы: «город …» префикс, хвост «…р-н, Ташкент», «Узбекистан, …»,
  уже чистая строка — идемпотентность).
- Юнит: сборка формата из компонентов (с district из БД и без).
- int-spec listings: create с координатами (геокодер замокан) → `address`/`address_en`.
- Live: создать объявление в визарде на staging/dev, проверить карточку на ru/en/uz.
